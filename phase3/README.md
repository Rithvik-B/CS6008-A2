# Phase 3 — DNSSEC Chain of Trust

Adds a cryptographic chain of trust to the Phase 1 hierarchy and re-runs the **Phase 2 attack
unchanged**. Only the zones and the resolver change; the attacker and its binary are identical to
Phase 2. Signing algorithm: **ECDSAP256SHA256 (alg 13)**.

## What changes vs Phase 2

- **Signed zones.** `sign/sign-all.sh` signs each zone child-first and builds the delegation chain:
  it signs `example.com`, publishes its **DS** in `com`, signs `com`, publishes its DS in the root,
  then signs the root. Each authoritative server loads its `db.*.signed` file.
- **Validating resolver.** The resolver enables `dnssec-validation yes` and installs **only** the
  root KSK as a static trust anchor (`config/resolver/trust-anchor.conf`, generated by the script).
  Root hints are unchanged.
- The attacker, its diversion route, and `attack/interceptor.c` are **unchanged** from Phase 2.

Generated material (`keys/`, `*.signed`, `trust-anchor.conf`, `build/`) is **not committed** — it
is regenerated by `sign/sign-all.sh`. No private key is in the repository.

## Deploy

```bash
docker build -t cs6008-dnslab:base ../common          # if not already built
docker run --rm -v "$PWD":/phase3 -w /phase3 cs6008-dnslab:base sign/sign-all.sh   # sign + chain
docker compose up -d
docker exec attacker make -C /attack                  # build the (unchanged) interceptor
```

## Verify (3.2) — healthy signed hierarchy (no interceptor in path)

```bash
docker exec resolver rndc -c /etc/bind/rndc.conf flush
docker exec client dig +dnssec example.com            # -> 172.16.1.20, header has the 'ad' flag + RRSIG
docker exec resolver delv -a /etc/bind/trust-anchor.conf @172.16.2.10 example.com   # -> "; fully validated"
docker exec client dig +short @172.16.2.10 com. DS            # com DS published in root
docker exec client dig +short @172.16.2.10 example.com. DS     # example.com DS published in com
```

## Attack (3.3) — re-run the Phase 2 forge, unchanged

```bash
docker exec core-router sh /diversion/divert-on.sh
docker exec -d attacker sh -c "exec /attack/interceptor eth0 172.16.2.10 172.16.1.30 forge > /tmp/forge.log 2>&1"
docker exec resolver rndc -c /etc/bind/rndc.conf flush
docker exec client dig example.com                    # -> status: SERVFAIL (rejected)
docker exec client dig +short example.com              # -> empty (no answer)
docker logs resolver 2>&1 | grep -E "RRSIG failed|no valid signature"
```

The interceptor still rewrites the `A` to `172.16.1.30`, but it cannot forge a matching RRSIG
(no private key), so the signature that reaches the resolver still signs `172.16.1.20` and fails
to verify — the resolver returns **SERVFAIL** and the client gets nothing.

## Files

- `sign/sign-all.sh` — signs all zones, builds the DS chain, writes the resolver trust anchor.
- `config/<node>/named.conf` — authoritative servers load `db.*.signed`; resolver has
  `dnssec-validation yes` + `include trust-anchor.conf`.
- `config/<node>/db.*` — unsigned zone **sources** (DS records are added by the script at sign time).
- `attack/`, `diversion/`, `www/`, `rogue-www/` — unchanged from Phase 2.
- `evidence/` — healthy-chain verify, SERVFAIL attack with the resolver's validation log, annotated capture.
