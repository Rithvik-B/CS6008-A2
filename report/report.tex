\section*{Overview}
\addcontentsline{toc}{section}{Overview}
This report documents a seven-phase study of DNS security carried out in a self-contained
Docker lab. We first stand up a plain hierarchical DNS service across three isolated subnets,
then mount an on-path forgery attack, add a DNSSEC chain of trust and re-run the attack, attempt
a signature-stripping downgrade, walk a signed zone, move the adversary to the client's last mile,
and finally encrypt that last mile with DoT. Each phase reports design choices, verification and
attack evidence (terminal output and annotated packet captures), and answers to the phase's
questions --- not only \emph{what} happened, but \emph{why}.

All nodes run on isolated Docker bridge networks; nothing touches the real Internet. Every attack
program is written in C/C++ with \texttt{libpcap}; \texttt{dig}, \texttt{delv}, \texttt{tshark},
and \texttt{curl} are used only to verify results. BIND 9.20.30 runs on every nameserver and on
the resolver.

\section{Phase 1 --- Building the DNS Hierarchy}

\subsection{Design}
The lab uses three Docker bridges --- client \texttt{172.16.1.0/24}, resolver
\texttt{172.16.2.0/24}, and authoritative \texttt{172.16.3.0/24} --- with IP masquerade disabled
on each. Docker's built-in inter-bridge isolation then drops any packet that tries to cross
directly between subnets, so the \emph{only} path between two subnets is a router container that
has an interface in both. The two routers (\texttt{edge-router}, \texttt{core-router}) enable
\texttt{net.ipv4.ip\_forward=1} with no NAT; every other node installs static \texttt{/24} routes
pointing at the router on its segment. Because a \texttt{/24} route is more specific than Docker's
default route via the bridge gateway, cross-subnet traffic is forced onto our routers.

The hierarchy is a faithful miniature of the real DNS: \texttt{root-ns} is authoritative for the
root and delegates \texttt{com} to \texttt{tld-ns} (glue \texttt{ns.com A 172.16.3.20});
\texttt{tld-ns} delegates \texttt{example.com} to \texttt{domain-ns} (glue
\texttt{ns.example.com A 172.16.3.30}); \texttt{domain-ns} serves \texttt{A} records for
\texttt{example.com} and \texttt{www.example.com} pointing at the webserver
(\texttt{172.16.1.20}). The resolver is recursive with \texttt{dnssec-validation no} and uses a
root-hints file that names only our private \texttt{root-ns}.

\subsection{Verification}
\textbf{Resolution and fetch.} From the client, \texttt{dig} returns the webserver address and
\texttt{curl} returns the legitimate page (full log: \texttt{phase1/evidence/p1\_resolve\_fetch.txt}):

\begin{lstlisting}
$ docker exec client dig +short example.com
172.16.1.20
$ docker exec client dig +short www.example.com
172.16.1.20
$ docker exec client curl -s http://example.com | grep -i legitimate
   <p>This is the <strong>legitimate</strong> site, served by webserver at 172.16.1.20.</p>
\end{lstlisting}

\textbf{Isolation.} A query sent straight to the authoritative subnet gets no answer, because the
client has no route into \texttt{172.16.3.0/24} --- it falls back to Docker's default gateway,
which does not forward between the isolated bridges:

\begin{lstlisting}
$ docker exec client dig +time=3 +tries=1 @172.16.3.10 example.com
;; communications error ... no servers could be reached
\end{lstlisting}

\subsection{Report answers}

\textbf{(a) Root $\rightarrow$ TLD $\rightarrow$ Domain referral --- what is visible on the wire.}
Captured on \texttt{core-router} (resolver-subnet interface) during one cold-cache resolution
(\texttt{phase1/evidence/p1\_referral.pcap}, decoded below):

\begin{lstlisting}
1  172.16.2.10 -> 172.16.3.10  query  A example.com
3  172.16.3.10 -> 172.16.2.10  resp   referral: com NS ns.com, glue A 172.16.3.20
4  172.16.2.10 -> 172.16.3.20  query  A example.com
6  172.16.3.20 -> 172.16.2.10  resp   referral: example.com NS ns.example.com, glue A 172.16.3.30
7  172.16.2.10 -> 172.16.3.30  query  A example.com
8  172.16.3.30 -> 172.16.2.10  resp   ANSWER: example.com A 172.16.1.20
\end{lstlisting}

Every message is plain, unauthenticated UDP/53. On the wire an observer sees, in cleartext: the
full query name (\texttt{example.com}) at every tier, the 16-bit DNS transaction ID and UDP
source port that tie a reply to its query, the referral NS names and their glue addresses, and
finally the answer \texttt{A 172.16.1.20}. Nothing is signed or encrypted; there is no field that
binds a reply to the genuine server beyond the ID/port pair, both of which are visible to anyone
on the path.

\textbf{(b) How the resolver's query reaches \texttt{root-ns}.} The resolver has no interface on
the authoritative subnet, so it uses the installed static route:

\begin{lstlisting}
$ docker exec resolver ip route get 172.16.3.10
172.16.3.10 via 172.16.2.3 dev eth0 src 172.16.2.10
\end{lstlisting}

The next hop \texttt{172.16.2.3} is \texttt{core-router}, which has a foot in both the resolver
and authoritative subnets and forwards the packet (\texttt{ip\_forward=1}, no NAT) out onto
\texttt{172.16.3.0/24} to \texttt{root-ns}. The reply returns by the symmetric path. This is why
the capture on \texttt{core-router} sees the entire referral chain.

\textbf{(c) What a node on the resolver's path could do.} Because the whole exchange is cleartext
and unauthenticated, any node that can see and relay the resolver's traffic --- exactly the
position \texttt{core-router} occupies, and the position the attacker will be given in Phase 2 ---
can read every query and, crucially, \emph{forge a reply}: it knows the transaction ID, the
source port, and the question, so it can craft a response that the resolver will accept as
genuine and cache. It can do this for one chosen name while relaying everything else untouched.
We exploit precisely this in Phase 2.

\section{Phase 2 --- On-Path Response Forgery}

\subsection{Design}
The adversary is placed on the resolver subnet at \texttt{172.16.2.100} and the client's rogue
server \texttt{rogue-web} at \texttt{172.16.1.30}. The resolver's inbound replies are diverted
through the attacker by a single route on \emph{core-router} only
(\texttt{diversion/divert-on.sh}):
\begin{lstlisting}
ip route replace 172.16.2.10/32 via 172.16.2.100   # on core-router
\end{lstlisting}
Every reply bound for the resolver is therefore handed to the attacker, which is now the sole
deliverer of answers to the resolver (there is no packet race --- the genuine reply physically
reaches us, not the resolver).

The interceptor (\texttt{attack/interceptor.c}, C + libpcap) captures each diverted reply, and in
\texttt{forge} mode rewrites \emph{only} the \texttt{A} record whose owner name is
\texttt{example.com} in the answer section to \texttt{172.16.1.30}; it then recomputes the IP and
UDP checksums, rewrites the Ethernet destination to the resolver's MAC, and \texttt{pcap\_inject}s
the frame onward. All other traffic --- the root and com referrals, glue, and
\texttt{www.example.com} --- is relayed byte-for-byte.

Two design points were essential. First, every non-router node is pinned to
\texttt{net.ipv4.ip\_forward=0}: Docker containers otherwise inherit \texttt{ip\_forward=1} from
the host VM, and the attacker's own kernel would forward the genuine reply to the resolver before
our forged one, defeating the attack and violating the ``only routers forward'' policy. Second,
the interceptor must recompute checksums on \emph{every} injected frame, because frames captured
on the Docker veth path carry offloaded (incomplete) UDP checksums that are invalid once injected
as raw bytes.

\subsection{Verification (2.2) --- transparent relay}
With forging disabled the interceptor relays every reply unchanged, so resolution is unaffected
(\texttt{phase2/evidence/p2\_verify\_relay.txt}):
\begin{lstlisting}
$ docker exec client dig +short example.com
172.16.1.20
$ docker exec client curl -s http://example.com | grep -i legitimate
   <p>This is the legitimate site, served by webserver at 172.16.1.20.</p>
[relay] relayed 117-byte DNS reply -> resolver (seen=4 forged=0)
\end{lstlisting}
This proves the attacker is genuinely on-path and that the diversion itself does not break DNS.

\subsection{Report answers}

\textbf{(a) What the resolver cached and what the fetch returned.} With forging enabled, the
client resolves the poisoned name and fetches the rogue page, while the non-target name is
unaffected (\texttt{phase2/evidence/p2\_attack.txt}, \texttt{p2\_nontarget.txt}):
\begin{lstlisting}
$ docker exec client dig +short example.com         # TARGET
172.16.1.30
$ docker exec client dig +short www.example.com      # non-target
172.16.1.20
$ docker exec client curl -s http://example.com | grep DEFACED
  <h1> example.com has been DEFACED </h1>
\end{lstlisting}
The resolver's cache dump confirms the poisoned record was accepted as an answer
(\texttt{phase2/evidence/p2\_cache.txt}):
\begin{lstlisting}
example.com.    3589  NS  ns.example.com.
; authanswer
                3589  A   172.16.1.30
www.example.com. 3589 A   172.16.1.20
\end{lstlisting}
The annotated capture on the attacker's NIC shows the interception and injection of the single
answer (\texttt{phase2/evidence/p2\_attack\_decode.txt}):
\begin{lstlisting}
frame  eth.src      ip.src        dns.a                      note
  7    core-router  172.16.3.30   172.16.1.20,172.16.3.30    GENUINE domain answer IN
  8    attacker     172.16.3.30   172.16.1.30,172.16.3.30    FORGED answer OUT -> resolver
\end{lstlisting}
The genuine \texttt{A=172.16.1.20} (frame 7) is rewritten to \texttt{172.16.1.30} (frame 8) and
delivered to the resolver; the root/com referrals that precede it are relayed unchanged.

\textbf{(b) Why the attack succeeds; the value of the on-path position.} Plain DNS answers are
\emph{unauthenticated}: the resolver accepts a reply solely because it matches the outstanding
query's transaction ID, UDP source port, and question --- none of which prove the reply came from
the genuine nameserver. An \emph{off-path} attacker who cannot see the query must \emph{guess}
those 16-bit fields (and win a race against the real reply), which is slow and unreliable. Our
\emph{on-path} position removes all of that: because we see (indeed, carry) the genuine reply, we
know the ID, port, and question exactly, and we simply edit the real answer in flight. There is no
guessing and no race --- the resolver's only copy of the reply is the one we hand it, so acceptance
is guaranteed.

\textbf{(c) How non-target names stay untouched.} The rewrite is gated on an exact owner-name
match: the interceptor decompresses each answer RR's owner name and rewrites the RDATA only when
it equals \texttt{example.com} and the type is \texttt{A}. Referrals (answer section empty), glue
records (owners \texttt{ns.com}/\texttt{ns.example.com}), and \texttt{www.example.com} never match,
so they are copied through verbatim. The interceptor log during a mixed run shows every
\texttt{www.example.com} reply relayed with \texttt{forged=0} and only the \texttt{example.com}
answer marked \texttt{REWRITTEN} (\texttt{phase2/evidence/p2\_nontarget.txt}).

\section{Phase 3 --- DNSSEC Chain of Trust}

\subsection{Design}
Each zone is signed with \textbf{ECDSAP256SHA256 (algorithm 13)} by \texttt{sign/sign-all.sh},
which works child-first so each child's DS can be published in its parent:
\texttt{example.com} is signed and its DS placed in \texttt{com}; \texttt{com} is signed and its DS
placed in the root; the root is signed last. Each authoritative server loads its \texttt{db.*.signed}
file. The resolver enables \texttt{dnssec-validation yes} and installs \emph{only} the root KSK as a
static trust anchor (\texttt{config/resolver/trust-anchor.conf}); its root hints are unchanged, and
the attacker, diversion route, and \texttt{interceptor.c} are identical to Phase 2.

Generated key material and signed zones are never committed --- they are reproduced by the signing
script. The DS chain produced on one run was:
\begin{lstlisting}
com.         IN DS 53993 13 2 0291B1A7EC52...527C370F      (published in root)
example.com. IN DS 365   13 2 1D9F6FA9DDC6...CF9C717A      (published in com)
trust anchor: . static-key 257 3 13 "/a1Fphw+kLLcqF1+gJxLkPcP..."   (root KSK)
\end{lstlisting}

\subsection{Verification (3.2) --- a healthy signed hierarchy}
With no interceptor in the path, the answer is authenticated end to end
(\texttt{phase3/evidence/p3\_verify.txt}):
\begin{lstlisting}
$ dig +dnssec example.com
;; flags: qr rd ra ad; ...                 <- the 'ad' (authenticated-data) flag is set
example.com. 3600 IN A     172.16.1.20
example.com. 3600 IN RRSIG A 13 2 3600 ... 19890 example.com. TVZej6fd...

$ delv -a trust-anchor.conf @172.16.2.10 example.com
; fully validated                          <- chain root KSK -> com DS -> example.com DS -> A
\end{lstlisting}

\subsection{Report answers}

\textbf{(a) What the resolver does with the forged response; how it differs from Phase 2; what it
checks.} The Phase 2 attack is re-run \emph{unchanged}. The interceptor still rewrites the
\texttt{A} record to \texttt{172.16.1.30}, but the outcome is now the opposite of Phase 2
(\texttt{phase3/evidence/p3\_attack.txt}):
\begin{lstlisting}
$ dig example.com
;; ->>HEADER<<- status: SERVFAIL ; ANSWER: 0
$ dig +short example.com
(empty)                          # the client gets nothing; curl fetches no page
[forge] ... example.com A REWRITTEN -> rogue-web   # the attacker is still forging
\end{lstlisting}
The resolver's own log says exactly what it checked and why it refused the answer:
\begin{lstlisting}
validating example.com/A: no valid signature found
RRSIG failed to verify resolving 'example.com/A/IN': 172.16.3.30#53
\end{lstlisting}
This is the difference from Phase 2. There, the resolver accepted any syntactically valid reply
that matched the query's ID/port/question. Here it additionally requires an \texttt{RRSIG} over the
\texttt{A} RRset that verifies under a \texttt{DNSKEY} which is itself vouched for by a \texttt{DS}
in the parent, up to the trust anchor. The attacker can change the \texttt{A} to \texttt{172.16.1.30}
but \emph{cannot} produce a matching signature --- it holds no private key --- so the RRSIG that
arrives still signs \texttt{172.16.1.20}. Signature verification over the tampered RRset fails and
the resolver returns SERVFAIL rather than serve unauthenticated data. The capture
(\texttt{p3\_attack\_decode.txt}) shows the forged \texttt{A=172.16.1.30} travelling with that stale
RRSIG.

\textbf{(b) Compared to Phase 1 on the wire: what can the attacker still read, and what does
DNSSEC protect?} Nothing on the wire became secret. DNSSEC \emph{signs} records; it does not
\emph{encrypt} them. The capture shows every query name, every answer (including the genuine
\texttt{172.16.1.20} and the attacker's \texttt{172.16.1.30}), the referral chain, transaction IDs
and ports --- all still in cleartext, exactly as in Phase 1. DNSSEC therefore provides
\emph{origin authentication and integrity} of DNS data (a resolver can tell a tampered or spoofed
record from a genuine one), but it provides \emph{no confidentiality}: an on-path observer still
learns what was asked and what the true answer is, and can still see (though no longer successfully
alter) the exchange. It also does not protect the last hop from resolver to a non-validating stub
(Phase 6), nor hide which names exist (Phase 5).

\textbf{(c) Signing-algorithm choice and private keys.} We chose \textbf{ECDSAP256SHA256
(alg 13)}: its 256-bit keys and signatures are far smaller than equivalent-strength RSA (RSASHA256
would need $\geq$2048-bit keys), which keeps responses small --- useful against UDP fragmentation
and amplification --- while validation stays fast; it is also the modern recommendation for new
deployments. The trade-off is that ECDSA verification is slightly more CPU-intensive per operation
than RSA and demands a sound random source at signing time. \textbf{No private key belongs in the
submitted repository}: the \texttt{K*.private} files and the signed zones are regenerated by
\texttt{sign/sign-all.sh}, and only the (public) trust anchor is needed by the resolver, itself
regenerated by the script. Committing a zone-signing private key would let anyone forge valid
signatures for the zone, destroying the very guarantee DNSSEC provides.

\section{Phase 4 --- Signature Stripping \& Downgrade}

\subsection{Design}
The Phase 3 signed hierarchy and validating resolver are reused unchanged. The interceptor gains a
\texttt{strip} mode: for \texttt{example.com} responses it re-emits the DNS message dropping the
zone's own-data security --- the \texttt{A}'s RRSIG, the \texttt{DNSKEY}, and the \texttt{DS} in the
com referral --- and rewrites the \texttt{A} to \texttt{172.16.1.30}. Crucially it \emph{keeps} any
\texttt{NSEC}/\texttt{NSEC3} record and the RRSIGs that cover them: those are the \emph{parent's}
authenticated statement about whether a secure delegation exists, which the attacker cannot forge.
The signing script takes a mode: \texttt{full} publishes \texttt{example.com}'s DS in \texttt{com}
(the Phase-3 chain); \texttt{nods} omits it (the child is signed but its DS was never given to the
parent).

\subsection{Report answers}

\textbf{(a) Run A --- stripping against the fully signed chain.} With the DS present, stripping the
signatures and even the DS fails (\texttt{phase4/evidence/p4\_runA.txt}):
\begin{lstlisting}
[STRIPPED example.com DNSSEC RRs (DS/RRSIG/DNSKEY)]   # attacker removes them on the wire
[STRIPPED example.com sigs + FORGED A]                # and injects A=172.16.1.30
$ dig example.com   ->  status: SERVFAIL     (dig +short: empty)
resolver log:  broken trust chain resolving 'example.com/A/IN'
\end{lstlisting}
The attacker \emph{can} delete bytes on the wire, but it \emph{cannot make the zone look legitimately
unsigned}. The reason \texttt{example.com} is treated as secure is the \texttt{DS} record published
in \texttt{com} --- and \texttt{com} is signed. To convince the resolver that \texttt{example.com} is
unsigned, the attacker would have to present \texttt{com}'s \emph{signed} statement that no DS exists
(a signed NSEC), which requires \texttt{com}'s private key. Stripping the DS on the wire just yields
an \emph{unsigned} ``no DS'' that the root-anchored resolver will not believe: it still holds a secure
delegation into \texttt{example.com}, finds no valid signature to complete the chain, and returns
SERVFAIL. Downgrade is resisted.

\textbf{(b) Run B --- the single change that reopens it.} The only change is in the \emph{parent}:
\texttt{com} publishes \textbf{no DS} for \texttt{example.com} (the child stays fully signed). Now
\texttt{com}'s signed \texttt{NSEC} \emph{authentically} proves that \texttt{example.com} has no DS,
so the resolver concludes the delegation is \emph{insecure}, stops requiring signatures for it, and
accepts the forged record (\texttt{phase4/evidence/p4\_runB.txt}):
\begin{lstlisting}
# baseline (no attacker): dig example.com -> 172.16.1.20, flags: qr rd ra   (no 'ad' -> insecure)
# attack (strip+forge):
$ dig example.com            -> status: NOERROR, flags: qr rd ra   (no 'ad')
$ dig +short example.com     -> 172.16.1.30
$ curl http://example.com    -> DEFACED page
\end{lstlisting}
The same strip-and-forge that failed in Run A now lands the client on the rogue page, because the
resolver never had a secure link into \texttt{example.com} to begin with.

\textbf{(c) Where downgrade resistance comes from, and the operator mistake that forfeits it.}
Downgrade resistance does not come from the child signing its zone --- in both runs
\texttt{example.com} is fully signed. It comes from the \textbf{authenticated DS in the parent}: the
signed \texttt{DS} is what tells a validator ``this delegation is secure, demand signatures,'' and
its \emph{signed absence} (NSEC) is what tells it ``this delegation is insecure.'' Because both the
presence and the absence are signed by the parent, an on-path attacker --- who holds no keys --- can
neither invent a secure delegation nor tear one down. The exact operator mistake that forfeits this
protection is the one in Run B: \textbf{signing the child but never publishing its DS in the parent}.
The zone looks protected (it has keys and RRSIGs) but is globally treated as unsigned, so the plain
Phase-2 forgery works again. Signing a zone is only half the job; the DS must reach the parent.
