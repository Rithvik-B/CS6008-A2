# Phase 1 — Building the DNS Hierarchy

Three-tier authoritative hierarchy (root → com → example.com), a recursive resolver with
DNSSEC validation **off**, a legitimate webserver, and two routers that are the only path
between the three isolated subnets. No attacker.

## Topology

| Container   | Subnet            | Address       | Role                                   |
|-------------|-------------------|---------------|----------------------------------------|
| client      | client 1.0/24     | 172.16.1.10   | issues `dig`/`curl`                    |
| webserver   | client 1.0/24     | 172.16.1.20   | serves legitimate example.com over HTTP|
| resolver    | resolver 2.0/24   | 172.16.2.10   | recursive caching resolver (no DNSSEC) |
| root-ns     | authoritative 3.0 | 172.16.3.10   | authoritative for root `.`             |
| tld-ns      | authoritative 3.0 | 172.16.3.20   | authoritative for `com`                |
| domain-ns   | authoritative 3.0 | 172.16.3.30   | authoritative for `example.com`        |
| edge-router | client+resolver   | .1.2 / .2.2   | forwards client ↔ resolver (no NAT)    |
| core-router | resolver+auth     | .2.3 / .3.3   | forwards resolver ↔ authoritative      |

Isolation comes from the topology: the three bridges have IP-masquerade disabled, so Docker's
own isolation drops any direct bridge-to-bridge traffic. The **only** path between subnets is a
router container with an interface in both. Routers forward (`net.ipv4.ip_forward=1`, no NAT, set
via compose `sysctls:`); every other node installs static `/24` routes via the router on its
segment (`STATIC_ROUTES` env → `node-entrypoint.sh`), which are more specific than Docker's
default route and so win.

## Deploy

```bash
# from repo root: build the shared base image (BIND 9.20.x on debian:trixie)
docker build -t cs6008-dnslab:base ../common
# from this directory:
docker compose up -d
```

## Verify

```bash
# 1. resolution + fetch
docker exec client dig example.com          # -> 172.16.1.20
docker exec client dig www.example.com       # -> 172.16.1.20
docker exec client curl -s http://example.com # -> the legitimate page

# 2. isolation: a direct query to the authoritative subnet must fail
docker exec client dig +time=3 +tries=1 @172.16.3.10 example.com   # -> no servers could be reached

# 3. capture one full resolution on core-router (resolver-subnet side)
docker restart resolver && sleep 3
docker exec -d core-router tcpdump -i eth1 -n -U -w /tmp/p1.pcap udp port 53
docker exec client dig example.com
docker exec core-router pkill -INT tcpdump
docker exec core-router tshark -r /tmp/p1.pcap -n -Y dns
```

## Teardown

```bash
docker compose down
```

## Files

- `compose.yml` — three bridges, eight services, static routes + router sysctls.
- `config/<node>/named.conf` + zone files — authoritative zones and the resolver's root hints.
- `www/index.html` — the legitimate example.com page.
- `evidence/` — terminal logs and the annotated referral capture used in the report.

Build artifacts (images, pcaps regenerated by the commands above) are not required to be
committed; `evidence/` holds the specific captures referenced by `report.pdf`.
